# Правила кода (пополняется ночным review_lite)

Выведены из реальных находок ревью. Читать перед правкой кода.

## 2026-07-17
- В списочных эндпоинтах не делать запрос к БД на каждую строку результата (N+1): агрегаты/связанные данные грузить пакетно одним запросом или JOIN-ом. _(источник: backend/routers/orders.py:75; backend/routers/orders.py:377)_
- Если функция уже принимает опциональный параметр загруженной сущности (например est=), переиспользовать его во всех внутренних вызовах, а не запрашивать одно и то же из БД повторно в рамках одного обработчика. _(источник: backend/routers/orders.py:75; backend/routers/orders.py:377)_

## 2026-07-20
- Производные денежные итоги (выплачено/факт) должны применять тот же инвариант «одна оплата = один факт», что и остальной код: не складывать creditors.paid и expenses.amount без исключения связанных (creditor_id / совпадение tx_id) записей — иначе покрытый платёж задваивается. _(источник: backend/routers/masters.py:300; backend/routers/masters.py:152; backend/db.py:40)_
- На fallback-ветке переоткрытия соединения с БД закрывать предыдущий handle перед повторным connect, чтобы не текли соединения при частичном сбое (connect прошёл, первый запрос упал). _(источник: backend/routers/masters.py:300; backend/routers/masters.py:152; backend/db.py:40)_

## 2026-07-21
- Признак «уже обработано/разнесено» нельзя строить на запросах, обёрнутых в `except Exception: pass`: при отсутствии таблицы, колонки или файла БД сущность молча станет «необработанной» и будет проведена повторно — такие сбои обязаны падать или логироваться с алертом. _(источник: backend/routers/payments.py:28; backend/routers/payments.py:95; backend/routers/payments.py:80)_
- Если выборка ограничена LIMIT, а часть строк отсеивается уже в Python, «запас» вида `limit * N` — молчаливая потеря данных: фильтровать в SQL либо возвращать явный признак усечения/курсор. _(источник: backend/routers/payments.py:28; backend/routers/payments.py:95; backend/routers/payments.py:80)_
- Новая запись сущности, для которой уже есть эндпоинт с валидацией и побочными эффектами (платёж, расход), должна создаваться через общую функцию этого эндпоинта, а не прямым INSERT в таблицу. _(источник: backend/routers/payments.py:28; backend/routers/payments.py:95; backend/routers/payments.py:80)_

## 2026-07-22
- PATCH обязан уметь очищать поле. Отсев `None` из `model_dump()` смешивает «поле не прислали» и «прислали null для очистки»: очистка молча теряется, ответ 200, значение старое. Использовать `model_dump(exclude_unset=True)`; пустые строки необязательных полей приводить к `NULL`. _(источник: backend/routers/suppliers.py:82)_
- Форматтеры не путают `0` и «нет значения». `if (!n) return "—"` прячет реальный ноль (закрытый долг, нулевой расход) как отсутствие данных. Проверять на `null`/`undefined`/`NaN`, не на falsy. _(источник: frontend/src/pages/wiki/helpers.ts:15; frontend/src/components/ui/priceMath.ts:17)_
- Подсказки/производные, зависящие от суммы по заказу, считать от фактического итога (SELECT SUM в той же транзакции после вставки), а не от нуля «потому что это первый платёж в обработчике». _(источник: backend/routers/orders.py:739; backend/routers/payments.py:182)_

## 2026-07-22
- Колонка, добавляемая ALTER-миграцией, обязана быть и в CREATE TABLE ленивой инициализации схемы (`_ensure_tables`/bootstrap), а сама миграция — быть no-op при отсутствующей таблице: иначе на чистой БД порядок «создали старую схему → INSERT новых колонок» падает, а стартовый ALTER роняет приложение. _(источник: backend/routers/catalog.py:11; backend/db.py:640; backend/routers/costing.py:60)_
- Резолв цены/справочника из внешней БД нельзя глушить `except Exception: pass`: недоступность прайсов должна отличаться от «позиция не найдена», иначе в себестоимость молча уходит 0 или лишний вопрос вместо явной ошибки/деградации. _(источник: backend/routers/catalog.py:11; backend/db.py:640; backend/routers/costing.py:60)_
- Если у ставки/цены есть схема начисления (fixed / per_unit / hourly / percent), схема обязана определять участие qty в формуле — единый `unit_price = rate` для всех схем тихо умножает фиксированную стоимость на количество. _(источник: backend/routers/catalog.py:11; backend/db.py:640; backend/routers/costing.py:60)_

## 2026-07-23
- Новый флаг/поле в единой точке записи (upsert) обязан иметь семантику «не передан → сохранить текущее значение»: параметр с дефолтом в ветке UPDATE молча затирает значение у всех вызывающих, которые о нём не знают. Использовать sentinel (None) и не включать поле в SET, если оно не задано. _(источник: backend/routers/rates.py:80; backend/routers/catalog.py:283; backend/routers/estimates.py:52)_
- Если у сущности есть «якорное» поле, введённое человеком (ручная цена), а рядом хранится производное от него (наценка, %), то полнотельный PUT обязан либо принимать якорь от клиента, либо восстанавливать его из существующей записи — иначе пересчёт от округлённого производного тихо меняет якорь при каждом сохранении. _(источник: backend/routers/rates.py:80; backend/routers/catalog.py:283; backend/routers/estimates.py:52)_

## 2026-07-24
- Операция, копирующая или разбивающая строку сущности, у которой есть производные движения по внешнему ключу (fund_transactions.expense_id, привязки контрагентов), обязана пересоздать эти движения и связи для КАЖДОЙ новой строки, а не только скопировать флаг-признак (payment_source): иначе движение остаётся одно на исходной строке и позднейшее удаление/правка части рассинхронит связанный контур. _(источник: backend/routers/orders.py:1091; backend/routers/orders.py:1088; backend/routers/finance.py:212)_

## 2026-07-25
- Обязательное поле в Pydantic-модели тела, которое обработчик не читает, — ловушка: обработчик берёт значение из пути/другого источника, а клиент шлёт пустое тело и получает 422. Поле, не используемое обработчиком, делать Optional или убирать; сверять поля модели тела с тем, что реально читается в теле и что отправляет фронт. _(источник: backend/routers/costing.py:495; backend/routers/costing.py:285; backend/routers/catalog.py:332)_
- Новый эндпоинт, использующий модуль/символ (datetime.utcnow, json и т.п.), обязан сам импортировать его в своём модуле, а не полагаться на импорт соседнего кода; для меток времени в SQLite предпочитать единый способ по файлу (datetime('now') в SQL либо Python-datetime), а не смешивать. _(источник: backend/routers/costing.py:495; backend/routers/costing.py:285; backend/routers/catalog.py:332)_

## 2026-07-27
- Множество «уже учтённых» переводов (seen-set) для дедупа факта по внешнему ключу (tx_id) обязано пополняться из ВСЕХ источников, способных нести этот ключ, включая строки, исключённые из суммы через NOT EXISTS/JOIN: иначе оплата, привязанная другим ключом (creditor_id) без переноса tx_id на покрывающую запись, всплывёт из внешнего источника и задвоится. _(источник: backend/routers/orders.py:258; backend/routers/orders.py:240; backend/routers/orders.py:138)_
- Функция агрегата, которую списочный эндпоинт зовёт в цикле, не должна внутри себя открывать внешнюю БД или делать полные сканы: тяжёлый предрасчёт передавать параметром (как transit_facts в list_orders) во ВСЕ её вызовы, включая suggest/подсказки, а не только в основной список. _(источник: backend/routers/orders.py:258; backend/routers/orders.py:240; backend/routers/orders.py:138)_

## 2026-08-01
- Признак, отделяющий новый контур от старого (extra_id IS NULL, order_id IS NULL, purpose IS NULL), обязан применяться во ВСЕХ ветках расчёта факта/суммы — включая альтернативные (транзитную, предрасчётную, агрегатную): фильтр, поставленный в одну ветку из двух, даёт двойной счёт в другой. _(источник: backend/routers/general_expenses.py:216; backend/routers/orders.py:630; backend/db.py:997)_
- Инвариант, описанный в комментарии или докстринге («не может стать меньше», «нельзя удалить»), обязан быть выражен кодом с явной ошибкой. Вычисленная, но не использованная в проверке величина создаёт иллюзию защиты и проходит ревью как реализованная. _(источник: backend/routers/general_expenses.py:216; backend/routers/orders.py:630; backend/db.py:997)_
- Пересборка таблицы SQLite (снятие NOT NULL и т.п.) обязана восстановить всё, что уносит DROP TABLE: индексы, UNIQUE/CHECK-ограничения, триггеры и остальные внешние ключи. PRAGMA table_info их не возвращает — список восстанавливаемого брать из sqlite_master, иначе схема тихо деградирует. _(источник: backend/routers/general_expenses.py:216; backend/routers/orders.py:630; backend/db.py:997)_

## 2026-08-02
- Внешний ключ, пришедший в теле запроса (extra_id, creditor_id, stock_parent_id), обязан проверяться на принадлежность той же родительской сущности перед записью: непроверенный id молча связывает деньги с чужим заказом, и обе карточки показывают одну и ту же оплату как свою. _(источник: backend/routers/orders.py:1592; backend/routers/orders.py:1509; backend/routers/orders.py:1195)_
- Поле-дискриминатор, разводящее контуры учёта (extra_id, purpose, order_id IS NULL), обязано переноситься КАЖДОЙ операцией, порождающей новые строки из существующей (split, копирование, списание), и не затираться дефолтом в полнотельном PUT: иначе новая или сохранённая строка молча возвращается в контур по умолчанию и портит там маржу. _(источник: backend/routers/orders.py:1592; backend/routers/orders.py:1509; backend/routers/orders.py:1195)_
- Если величина исключена из итога (fact), она обязана быть исключена и из детализации этого же итога (sources/разбивка по категориям) либо детализация должна возвращать собственный итог: расхождение «сумма строк ≠ показанный итог» проявляется только в UI и не ловится тестами бэкенда. _(источник: backend/routers/orders.py:1592; backend/routers/orders.py:1509; backend/routers/orders.py:1195)_

## 2026-08-03
- Денежная величина, которую видит клиент в двух разных документах по одной сущности (счёт и КП, счёт и договор), обязана считаться одним вызовом с одинаковыми параметрами округления и одинаковыми дефолтами недостающих ставок: расхождение проявляется только у клиента и бэкенд-тестами не ловится. _(источник: backend/routers/estimates.py:1111; backend/routers/estimates.py:1112; backend/routers/estimates.py:678)_
- Успешность внешнего генератора файлов нельзя определять по наличию файла с детерминированным именем — файл предыдущего запуска маскирует провал. Путь результата брать из вывода генератора (явный маркер) или писать в уникальный путь на запуск и удалять старый до вызова. _(источник: backend/routers/estimates.py:1111; backend/routers/estimates.py:1112; backend/routers/estimates.py:678)_
- Общий счётчик/последовательность в файле обновлять только атомарно (блокировка + запись во временный файл и rename): read-modify-write из нескольких процессов возвращает одинаковые номера, а объединение счётчиков без блокировки лишь переносит гонку в одно место. _(источник: backend/routers/estimates.py:1111; backend/routers/estimates.py:1112; backend/routers/estimates.py:678)_

## 2026-08-04 (спека ЛЕСКОВО, Б3 — решение Юры)
- Деньги остаются в REAL, дисциплина вместо смены типа: любая сумма проходит `money(x)` (backend/money.py, round до 2 знаков) перед записью в базу; суммы НЕ сравниваются на строгое равенство — только `abs(a-b) < 0.01`. Переход на INTEGER-копейки не делаем: переписывание всего кода ради проблемы, которой нет. _(источник: спека 2026-08-04-leskovo-adoption-design)_

## 2026-08-04
- Пересборка таблицы, вводящая CHECK/NOT NULL, обязана сначала привести существующие данные к новому инварианту (UPDATE канонизации + явная проверка SELECT-ом с отказом от пересборки и алертом при остатке), а не полагаться на `INSERT … SELECT`: стартовая миграция падает на одной легаси-строке и роняет весь сервис. Временную таблицу создавать только после `DROP TABLE IF EXISTS <t>_new` — иначе первый сбой делает старт невозможным навсегда. _(источник: backend/db.py:1310; backend/db.py:1345; backend/db.py:1332)_
- Набор колонок при пересборке таблицы брать из фактической схемы (PRAGMA table_info + sqlite_master), а зашитым DDL описывать только добавляемые ограничения: в общей базе, куда пишут несколько агентов, зашитый список колонок молча удаляет чужие поля вместе с данными. Осознанное отбрасывание колонки должно быть явным списком и печататься в лог. _(источник: backend/db.py:1310; backend/db.py:1345; backend/db.py:1332)_
- Контекст запроса (актор, tenant, request-id) нельзя передавать через ContextVar, установленный в синхронной FastAPI-зависимости: она исполняется в threadpool с копией контекста, и значение до обработчика не доезжает — передавать параметром зависимости, через request.state или ставить в middleware. _(источник: backend/db.py:1310; backend/db.py:1345; backend/db.py:1332)_

## 2026-08-05
- Новый эндпоинт записи денежной сущности обязан прогонять тело через уже существующую валидацию этой сущности (payment_source, подотчётное лицо, категория, существование ссылок), а не свой урезанный набор проверок: побочные контуры (касса, подотчёт, лицевой счёт) получают строку, которую основной вход бы отверг. _(источник: backend/routers/ledger.py:121; backend/routers/ledger.py:300; backend/routers/ledger.py:75)_
- Регистр, собираемый из нескольких таблиц, обязан связывать источники по идентификатору, а не по человекочитаемому имени: переименование сущности или тёзка молча меняют сальдо и не дают ни ошибки, ни расхождения в логах. _(источник: backend/routers/ledger.py:121; backend/routers/ledger.py:300; backend/routers/ledger.py:75)_
- Диагностическая проверка («готовность», сторож, список аномалий) не имеет права возвращать пустой результат при сбое доступа к источнику — пустой список читается человеком как «ошибок нет»: возвращать явный признак деградации и показывать его в UI. _(источник: backend/routers/ledger.py:121; backend/routers/ledger.py:300; backend/routers/ledger.py:75)_
